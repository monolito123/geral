# Minimal Linux test target

A very small Linux system that boots in QEMU in a few seconds. It exists so
that NottOS components that live in or next to the kernel can be exercised
on any development machine and in CI, without an AOSP build host.

**It is not NottOS.** It contains no Android code and no hardware root of
trust. The only NottOS product code in it is the verification tool that its
boot stage calls. Passing these tests says nothing about the Cuttlefish
target or about any phone. See
[ADR-0007](../../docs/adr/0007-minimal-linux-test-target.md).

## What it is made of

| Piece | Stands in for | Notes |
|---|---|---|
| Distribution kernel, unmodified | The device kernel | Newest `linux-image-*-generic` from apt; version recorded in `kernel-version` |
| `initramfs.cpio.gz` (stage 1) | The bootloader-verified boot image | Carries the trusted release public key and `nott-tools`. Nothing verifies the initramfs itself: QEMU loads whatever it is given. |
| `meta.img` | Signed boot metadata (what `vbmeta` is on Android) | The root hashes of the system and integrity-folder images, a manifest listing them, and its hybrid signature for the purpose `boot-metadata`, in four fixed slots with no filesystem, so nothing is parsed before the signature is checked |
| `system.img` + `system.verity` | The read-only system partition | EROFS under dm-verity, opened with the root hash the signed boot metadata vouches for |
| `attest.img` + `attest.verity` | The integrity-folder partition (ADR-0010) | Mounted read-only at `/nott/attest`; holds the signed build manifest, the release keys in NottOS and OpenPGP form, and the README |
| `data.img` | The user-data partition | dm-crypt over the whole partition (as metadata encryption does), ext4 with one fscrypt-protected directory (as credential-encrypted storage does) |
| `scratch.img` | A vendor state partition | Plain ext4, mounted `nosuid,nodev,noexec`, on the exception list |
| `nott-seal` | The kernel side of the network seal (ADR-0014) | tc, iptables and arptables, the facilities the Android generic kernel has |
| `fscryptctl` | `vold`'s use of the kernel's fscrypt interface | Google's reference tool, built from commit `f1ec9198` (v1.3.0); the distribution does not package it |

The data-partition key is a fixed test key inside the boot image. On a phone
that key is wrapped by the TEE and bound to the verified-boot state. Here it
protects nothing against someone who holds the boot image.

The signing keys are test keys generated by every build and kept, secret
halves included, in `out/mini/keys`.

Not covered: rollback. An older system image with its own authentic
metadata would boot. Anti-rollback belongs to the update system.

## Running

```sh
./nott mini test     # build the images and run every test
./nott mini shell    # boot to an interactive shell on the serial console
```

Needs: `qemu-system-x86`, `erofs-utils`, `cryptsetup-bin`, `dmsetup`,
`e2fsprogs`, `kmod`, `cpio`, `zstd`, `busybox-static`, `openssl`, `gnupg`,
`iproute2`, `iptables`, `arptables`, and apt
access to download the kernel packages (about 180 MB, cached under
`out/mini/cache`). KVM is used when `/dev/kvm` is writable; otherwise QEMU
emulates, which takes a few seconds per boot.

## Tests

| Test | What is done | What must happen |
|---|---|---|
| T1 | Boot the untampered images | Stage 1 accepts the manifest signature by the trusted key; the system reaches the shell marker from the verified image; a 64 KiB file reads back with the expected digest |
| T2 | Flip one bit in a block that boot reads | Never reaches the shell marker; the kernel logs dm-verity corruption |
| T3 | Flip one bit in a block that boot does not read | Boots; reading the affected file fails with an I/O error; tampered data is never returned |
| T4a | Boot metadata signed by a key the boot image does not trust | Stage 1 refuses: "signature was made by a different key" |
| T4b | Manifest changed after it was signed (still well-formed) | Stage 1 refuses: "signature is not valid for this key and message" |
| T4c | System root hash replaced; manifest and signature untouched | Stage 1 refuses: the root hash does not match the signed manifest |
| T4d | Integrity-folder root hash replaced | Stage 1 refuses, as in T4c |
| T5 | Write secrets, power off, inspect the raw disk; then boot without the passphrase, with a wrong one, with the right one | File content and file name are absent from the raw image; without the right passphrase the name is unreadable and the content inaccessible; with it the content is intact |
| T6 | Collect the mount table and check it with `nott-tools storage check` | Every mount is verified read-only, volatile, a kernel interface, encrypted, or the listed exception |
| T7a | Inspect the integrity folder in the running system, as root | Mounted read-only from the verified image; creating, appending, deleting, renaming, making a directory, remounting writable, and writing the verity device or the disk are all refused; the signed manifest matches the system image and its hash tree |
| T7b | Check the integrity folder from the host, with `nott-tools` and with GnuPG | Every image matches, including the boot image; the OpenPGP signature verifies; an edited copy of the manifest fails both checks |
| T7c | Flip one bit in the folder's manifest | Reading it fails with an I/O error, the in-system check fails, and the kernel reports dm-verity corruption |
| T8a | Boot sealed and never unseal: bring the interface up with IPv6 on, try DHCP, ARP, ping, DNS, TCP and IPv6 ping, while the host tries to connect to the machine's port 8080 once a second | Every attempt fails; the seal counted drops at the IP layer and at the device layer in both directions; QEMU's capture, which starts before the machine does, holds no frame sent by the machine and at least one sent to it |
| T8b | Unseal (the stand-in for an authenticated unlock), use the network, seal again, try everything once more; the host starts its connection attempts only once the machine reports that it sealed itself again | While open: a DHCP lease, an ARP reply, and frames of every kind in the capture. After sealing: every attempt fails, and the capture holds no frame sent after the last frame of the open phase |
| T8c | Boot with one of the packet-filter modules blocked | Stage 1 stops before anything else; no frame is sent |
| T9a | With `init_on_free=1`: add a storage key, write a file under it, keep a copy of the key in memory as a key manager does; then lock with the file still open, stop the process holding it, and remove the key. The host searches the machine's memory, from outside, at each step | While unlocked, the search finds the key and the content (control). With the file open, removal is incomplete and the content is still in memory. After the holder is stopped: the key is absent, the file unreadable, and neither key nor content is anywhere in memory |
| T9b | The same with the kernel's default, without `init_on_free=1` | The content survives in freed memory after the key is removed, as the kernel documentation warns, which shows that T9a's result comes from the setting |

Each test that expects absence has a control that shows the check can fail:
the raw-disk scan must find a plaintext canary on the unencrypted scratch
disk, the storage check must flag that disk when the exception list is
withheld, and the capture checker must flag T8b's capture when told the
machine was sealed throughout.

## Relation to the roadmap

T1 to T6 are scaled-down analogues of Phase 1 acceptance criteria 1.2 to
1.6. T8a and T8b are analogues of Phase 4 criteria 4.1 and 4.2 (invariants
INV-05 and INV-08), on one wired interface and without radios. T9a is an
analogue of Phase 2 criterion 2.6 for one evict-on-lock storage class
(INV-09), without a TEE and without inline encryption hardware. They do not satisfy those criteria, which are about the Cuttlefish
target, where the bootloader does the first verification.
