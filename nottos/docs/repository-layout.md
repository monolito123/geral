# Repository layout and engineering standards

- **Version:** 0.1 (Phase 0 draft, awaiting owner approval)
- **Date:** 2026-11-12

Only `docs/` exists today. Everything else below is planned and is created
when its first real content lands, not before. No placeholder files.

## 1. How an AOSP derivative is organised

AOSP is not one repository. It is roughly a thousand Git repositories tied
together by a manifest that pins each to a revision `[K]`. NottOS therefore
has three kinds of source:

| Kind | What | Where it lives |
|---|---|---|
| **Upstream, unmodified** | The AOSP projects NottOS does not change | Fetched from AOSP at the tag the manifest pins |
| **Upstream, patched** | The AOSP projects NottOS changes (framework, core system, policy, kernel and a few others) | A NottOS fork of each, on a branch rebased onto each upstream tag |
| **NottOS's own** | New daemons, libraries, apps, policy, device descriptors, tools, tests, documents | This `nottos/` tree |

Patched upstream projects can be kept as forked repositories (the common
practice among AOSP derivatives, easy to rebase) or as patch series stored in
this tree and applied after checkout (one repository, but fragile).
Recommendation: forks, which needs a dedicated organisation with many
repositories. That is decided in a Phase 1 ADR and depends on the owner
(requirements review, Q6). Until then `nottos/` lives in this general
repository.

## 3. Rules that follow from the brief

### Builds and releases

- **One command** builds everything from a clean checkout:
  `nott build <target>`. It does not exist yet.
- **Pinned toolchains.** The manifest pins AOSP's prebuilt compilers; a
  toolchain file pins the Rust version for host tools. Nothing is fetched
  from the network during the build.
- **Reproducible.** Two clean builds of the same manifest must produce
  identical images. A comparison tool reports any difference; each
  difference is a bug.
- **Software bill of materials** generated by the build in SPDX format,
  listing every component, version, hash and licence.
- **Signed releases** with the hybrid scheme. Test keys live in the tree and
  are named as such. Release keys never touch a networked machine or this
  repository. The key ceremony is a written procedure under
  `docs/process/`.

### Code quality

- Small changes, each reviewed before merge. Commit messages in English, in
  the form `component: summary`.
- No dead code, no commented-out code, no secrets in the repository.
- Every `unsafe` block in Rust has a `// SAFETY:` comment that states why it
  is sound, and a test that exercises it.
- Every assembly file sits in an `arch/<architecture>/` directory next to
  its portable reference implementation. Its header comment states what it
  replaces, the measured gain and on which hardware, and where its
  differential test and benchmark are.
- Compiler warnings are errors. Lints are enforced in CI.

### Testing

| Kind | Where it runs |
|---|---|
| Unit tests | Build host, on every change |
| Integration tests | Emulator, on every change |
| CTS and VTS | Emulator nightly; each supported device before release |
| Fuzzing of every parser and IPC surface | Continuously |
| Sanitizer builds (address, undefined behaviour, kernel, memory tagging) | Nightly |
| Locked-state tests | Emulator on every change; hardware before release |
| Performance regression against budgets | Device lab nightly, once it exists |

### Licensing `[P]`

To be fixed by an ADR in Phase 1. Proposal:

| Code | Licence | Reason |
|---|---|---|
| New NottOS user-space code | Apache-2.0 | Same as most of AOSP, so code can move in both directions; explicit patent grant; acceptable to hardware partners |
| Kernel patches and the seal hook | GPL-2.0-only | Required by the kernel |
| Changes to an existing project | That project's licence | Required |
| Documentation | CC BY 4.0 | Reusable with attribution |

Reused components keep their licences. Copyleft apps shipped as separate
packages (for example a GPL keyboard or eSIM manager) are compatible with
this, because they are separate works. Each such choice is recorded in the
component's ADR and in the SBOM. The kernel's GPL obligations are met by
publishing the exact kernel source and configuration for every release.

### Security process

- Security patches are merged as soon as upstream publishes them. Upstream
  now publishes most fixes quarterly and high-risk fixes monthly
  `[V:F-13]`; NottOS follows both and shows the patch level and its age in
  the Verify app.
- A vulnerability disclosure policy with a contact, a response time and an
  embargo period, published under `docs/process/`.
- An independent security audit before any stable release.

### Documentation

Architecture overview, threat model, ADRs, porting guide, and a user guide
in Brazilian Portuguese and English. User-facing text is written in both
languages from the start, Brazilian Portuguese first.
