# Fact check — fast-moving facts

Checked on **2026-11-12**. Each entry records what was checked, where, and how
much weight it can bear. Design documents cite these as `[V:F-nn]`.

Confidence levels:

- **Primary** — read on the publisher's own page in this check.
- **Secondary** — reported by press, a project's social account or a search
  summary; the primary page was not read. Re-check before relying on it for an
  irreversible decision.
- **Not verified** — attempted, could not be confirmed. Listed so nobody
  assumes it was.

| F-23 | File-based encryption. Storage classes are device-encrypted (available at boot) and credential-encrypted (after first unlock). The credential is stretched with scrypt "targeting a time of about 25 ms and a memory usage of about 2 MiB"; Weaver (secure element or TEE) or Gatekeeper enforces rate limiting. Keys not bound to a credential are wrapped by a rollback-resistant Keystore key. ## Cryptography standards

| ID | Fact | Confidence | Source |
|---|---|---|---|
| F-06 | NIST: FIPS 203 (ML-KEM), FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA) are final (August 2024). Falcon (to become FN-DSA) and HQC are "selected for ongoing standardization; that process is underway". Secondary sources disagree on whether a FIPS 206 draft has been published; treat FN-DSA and HQC as **not standardised**. Page updated 2026-10-27. | Primary | [NIST CSRC PQC project](https://csrc.nist.gov/projects/post-quantum-cryptography) |
| F-07 | Google (2026-03-25): in Android 17 the AVB library integrates ML-DSA; Android Keystore exposes ML-DSA-65 and ML-DSA-87; remote attestation begins moving to PQC; the platform verifies PQC signatures over APKs; Play App Signing produces hybrid classical + PQC signature blocks. The post does **not** say which parameter set AVB uses, whether AVB signatures are hybrid, or whether bootloaders of existing devices will be updated. | Primary | [Google security blog](https://blog.google/security/security-for-the-quantum-era-implementing-post-quantum-cryptography-in-android/) |
| F-29 | The IETF composite-signature specification (`draft-ietf-lamps-pq-composite-sigs`) is still an Internet-Draft (revision 19, April 2026). It pairs ML-DSA with RSA, ECDSA, Ed25519 and Ed448; downstream drafts show ML-DSA-44 and ML-DSA-65 paired with Ed25519, and ML-DSA-87 with ECDSA P-384. Its message representative is a prefix, a label, a context length, a context and a pre-hash of the message. | Secondary (search of IETF archives) | [IETF LAMPS drafts](https://bgpupdates.potaroo.net/ietf/html/ids-wg-lamps.html) |
| F-30 | Rust implementations, read from the published crates on 2026-11-13: `libcrux-ed25519` 0.0.10 describes itself as a "Formally verified ed25519 signature library" and calls HACL\* code; `libcrux-ml-dsa` 0.0.11 states "The portable and AVX2 code for field arithmetic, NTT polynomial arithmetic, and serialization is formally verified using hax and F*"; RustCrypto `ml-dsa` 0.1.2 states "The implementation contained in this crate has never been independently audited!". | Primary (crate sources and documentation) | [libcrux](https://github.com/cryspen/libcrux), [ml-dsa](https://docs.rs/ml-dsa/0.1.2/ml_dsa/) |
| F-32 | SLH-DSA in Rust, read from the published crates on 2026-11-13: `fips205` 0.5.0 states it "implements the released FIPS 205 standard in pure Rust ... without any unsafe code" and that "Key generation and signing are constant-time", "Checked by source review, by counting hash calls in all twelve parameter sets, and by the dudect measurements"; it makes no audit claim. RustCrypto `slh-dsa` 0.1.0 states "The implementation contained in this crate has never been independently audited!". No formally verified Rust SLH-DSA was found. | Primary (crate sources) | [fips205](https://github.com/integritychain/fips205), [slh-dsa](https://github.com/RustCrypto/signatures) |
| F-33 | The Kernel Self Protection Project publishes recommended kernel settings (configuration options per architecture, command-line options and sysctls) at kspp.github.io/Recommended_Settings. Read on 2026-11-14; the page shows no last-updated date. Among them: CFI with Clang, shadow call stack, PAC, BTI and MTE on arm64, `INIT_ON_ALLOC/FREE_DEFAULT_ON`, lockdown, strict IOMMU, and `MODULES` unset or, if modules are needed, `MODULE_SIG_FORCE`. | Primary (page read through a summarising fetch; option names as listed) | [KSPP](https://kspp.github.io/Recommended_Settings) |
| F-34 | Hybrid KEM drafts: X-Wing (`draft-connolly-cfrg-xwing-kem`, revision 11, September 2026, independent submission) combines X25519 with ML-KEM-768. Composite ML-KEM (`draft-ietf-lamps-pq-composite-kem`, revision 18 the latest seen) uses `SHA3-256(mlkemSS || tradSS || tradCT || tradPK || Label)` and lists pairings such as ML-KEM-768 with X25519 and ML-KEM-1024 with X448 or P-384; no ML-KEM-1024 with X25519 was found. Neither is an RFC. Implementations read on 2026-11-14: `libcrux-ml-kem` 0.0.11 ("formally verified using hax and F*"; constant-time patterns validated "via inspection of the generated assembly"), `libcrux-curve25519` 0.0.9 ("Formally verified curve25519 ECDH library"), RustCrypto `ml-kem` 0.3.4 ("has never been independently audited"). | Drafts: secondary (search of IETF archives). Crates: primary (sources). | [Composite ML-KEM](https://datatracker.ietf.org/doc/html/draft-ietf-lamps-pq-composite-kem), [X-Wing](https://datatracker.ietf.org/doc/html/draft-connolly-cfrg-xwing-kem) |
| F-31 | NIST publishes ML-KEM, ML-DSA and SLH-DSA test vectors in the ACVP-Server repository; the files used are identified by commit and SHA-256 in `core/crypto/tests/vectors/README.md`. | Primary | [ACVP-Server](https://github.com/usnistgov/ACVP-Server) |

Cuttlefish needs hardware virtualisation (F-25). Neither is available here,
so AOSP cannot be built or booted in this environment. Host-side Rust
components and a minimal Linux system in QEMU can.
