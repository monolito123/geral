# ADR-0015: Storage key hierarchy and eviction at lock

- **Status:** Accepted (2026-11-14; decided under the owner's delegation)
- **Date:** 2026-11-14
- **Decider:** project owner (delegated)

## Context

The brief (section 9) asks for per-profile and per-file keys, keys evicted
from memory when the device locks, a memory-hard function for the
credential, and the SoC's inline encryption engine where it can be trusted.
The architecture (sections 5.1 and 5.2) gives the outline; the owner chose
graded eviction (requirements review, Q1 and C-05); C-21 records the
trade-off between per-file keys and the inline engine. Criterion 2.6 asks
that keys be evicted on lock and on reboot; invariant INV-09 says that after
lock the keys of evict-on-lock classes are absent from kernel and process
memory.

What upstream provides:

- Two storage classes per profile: device-encrypted (DE, available at boot)
  and credential-encrypted (CE, available after the first unlock). The
  credential is stretched with scrypt, about 25 ms and 2 MiB, and the
  guess limit is enforced by Weaver or Gatekeeper `[V:F-23]`.
- Keystore keeps an after-first-unlock super key until reboot, and an
  unlocked-device-required super key that it clears at every lock, **unless
  a weak unlock method is enabled**; with class 3 biometrics it keeps a
  biometric-encrypted copy `[V:F-41]`.
- Hardware-wrapped keys, optional since Android 11 `[V:F-40]`.

What the kernel guarantees when a key is removed `[V:F-39]`: the master key
is wiped and cached inodes are evicted; keys of files still in use are not
removed ("incompletely removed"); decrypted contents are freed **but not
wiped** unless `init_on_free=1`; copies held by user space are user space's
problem. GKI kernels zero memory on allocation but not on free
`[V:F-42]`.

Measured on the test target (T9a, T9b) with a 4 MiB file of 64,000
identical lines:
- With a file still open, removal is incomplete and the plaintext stays
  in memory.
- Once the holder is stopped and the key removed, neither key nor
  plaintext is anywhere in RAM with `init_on_free=1`.
- Without `init_on_free=1`, about 63,000 of the lines are still in freed
  memory, in each of the runs made.

With a file of two pages, the control without `init_on_free=1` found
plaintext in one run and none in the next: recently freed pages are
reused, and zeroed, first. The test therefore uses a file large enough
that most of it is not reused at once.

## Options considered

### Eviction at lock

| Option | Assessment |
|---|---|
| Evict the main profile's CE key at every lock | Rejected by the owner (Q1): most apps stop working while locked |
| **Graded: a new unlocked-only class (UL) beside DE and CE, chosen per app by the owner** | Chosen (Q1) |
| Rely on apps encrypting their own data with unlocked-device-required Keystore keys | Needs app changes; NottOS cannot make unmodified apps do it. A complement, not the mechanism |

### Credential stretching

| Option | Assessment |
|---|---|
| Upstream scrypt alone | Cheap per guess once the hardware gate is defeated |
| Replace scrypt by Argon2id | Diverges from upstream's protector format and migration paths |
| **Argon2id before upstream scrypt** | Chosen: the upstream chain, the gate and the formats stay as they are |

### File keys

As C-21: per-file keys in software, or one hardware-wrapped contents key
per class with the inline engine. Both are kept, chosen per device.

## Decision

### Classes, per profile

| Class | Available | Key wrapped by | Evicted |
|---|---|---|---|
| DE | From boot | A TEE key bound to the verified-boot state, rollback-resistant | Reboot |
| CE | From first unlock | The synthetic password, through Weaver or Gatekeeper | Reboot; end of the profile's session |
| **UL** (NottOS) | While unlocked | A Keystore key with unlocked-device-required, bound to the profile | **Every lock**; reboot; end of session |

### The unlocked-only class

- **Keys.** One fscrypt v2 master key per profile, generated by `vold`, in
  software or hardware-wrapped form like the others.
- **Unlock.** `vold` unwraps the key (possible only while unlocked), adds
  it to the kernel and wipes its own copy. Keys in user space are held in
  locked memory and wiped after use.
- **Lock.** On `seald`'s signal, every process with a UL file open is
  stopped, then the key is removed. If the kernel still reports it as
  incompletely removed, the remaining holders are stopped and the removal
  is repeated until the kernel reports it absent. A file still open keeps
  its plaintext in memory (T9a), so stopping holders is part of the
  mechanism, not an optimisation. Proposed bound: 500 ms from lock to key
  absent `[P]`.
- **Who uses it.** Apps the owner opts in, in Settings; apps need no new
  API. An opted-in app is stopped at every lock and cannot run, notify or
  sync until unlock; Settings says so. Opting in moves the app's data into
  a new UL directory while the app is stopped. Profiles and the private
  space can also be set to end at lock, which evicts their CE keys as
  upstream does when a user stops.
- **Weak unlock methods** (trust agents, biometrics below class 3) are
  disabled, since keystore keeps the unlocked-only super key in memory while
  one is enabled `[V:F-41]`. Class 3 biometrics remain available; keystore
  then holds only a copy encrypted by a key the TEE releases for a fresh
  biometric match.
- **Backups** (ADR-0013) read UL data only while unlocked. The backup key
  itself is CE: backups of CE data can run while locked, and the backup key
  cannot read backups anyway.

### Memory

- Memory is zeroed when freed: `INIT_ON_FREE_DEFAULT_ON` in kernels NottOS
  builds (ADR-0011), and `init_on_free=1` on the command line of GKI
  kernels, which lack it `[V:F-42]`. T9b shows what is left otherwise.
- Key material in `vold`, keystore and `seald` is never swapped, written to
  logs or kept after use.

### File keys

- Where the device audit trusts the inline engine and it supports
  hardware-wrapped keys: wrapped keys, `inlinecrypt`, one contents key per
  class (`IV_INO_LBLK_64`; not `IV_INO_LBLK_32`, which reuses IVs
  `[V:F-39]`). Raw master and contents keys then never sit in kernel
  memory; filename keys still do.
- Elsewhere: software encryption with per-file keys: AES-256-XTS for
  contents, AES-256-HCTR2 or CTS for names, Adiantum on CPUs without AES
  instructions.
- The choice is recorded per device in its capability descriptor and shown
  on the security posture screen.

### Credential stretching

```text
stretched = upstream_scrypt( Argon2id(credential, salt, m, t, p) )
```

The salt is random per profile and stored with the protector; everything
after the stretch, the hardware gate included, is upstream's. The
implementation is `nott-crypto`'s Argon2id (vectors and a second
implementation in its tests, ADR-0013), called from `system_server` through
JNI. Parameters per device class are chosen so that the stage takes at most
a quarter of the unlock budget (performance budgets, section 2.7): 250,
150 and 100 ms for classes L, M and H. The starting point, until measured
on reference hardware, is 64 MiB, one pass, four lanes `[P]`; three passes
of 64 MiB took 0.21 s on the development machine, which is not a phone.

This protects passphrases. It does not make a six-digit PIN safe once the
hardware gate is defeated; Tier B devices without a secure element should
require a passphrase (architecture, section 5.1).

### Eviction events

| Event | Evicted |
|---|---|
| Lock | UL keys of every profile; the unlocked-device-required super key; CE keys of profiles set to end at lock |
| End of a profile's session | That profile's CE and UL keys and super keys |
| Reboot, auto-reboot, forced reset | Everything |
| Duress credential | Everything, and the Weaver slots and TEE keys needed to derive it again |

## Consequences

- **Positive:** a locked device holds no key or plaintext of UL data, as
  measured on the test target; the upstream key chain and gate are
  unchanged; per-device choice of inline or software encryption is
  explicit.
- **Negative:** apps in UL stop at every lock; locking takes longer; weak
  unlock methods are gone; `vold`, keystore and `system_server` carry
  NottOS patches.
- **Risks:**
  - *The main profile's CE key stays in memory while locked* (Q1). The
    auto-reboot timer bounds the time.
  - *A system process holds a UL file* (an indexer, a backup in progress).
    It must be stopped like an app; UL data is excluded from media
    indexing.
  - *Cold-boot attacks* in the moments after lock; hardware-wrapped keys
    narrow them where available.
  - *ADR-0011's checker reads kernel configuration only*: on GKI kernels it
    cannot see `init_on_free=1` on the command line. Command-line rules are
    needed in the profile.
  - The Argon2id cost at unlock is unmeasured on phones.

## Revisit when

- Phase 3 integrates `vold`, keystore and `seald` on Cuttlefish.
- Reference hardware timings for the credential stretch exist.
- Upstream changes the keystore super-key behaviour.

## Verification

- Test target, T9a: with `init_on_free=1`, the host searches the machine's
  RAM from outside while unlocked (finds key and content: the search
  works), during an incomplete removal (content still present), and after
  lock (neither present; file unreadable; key status absent).
- T9b, the control: the same without `init_on_free=1`, content found in
  freed memory after lock.
- On Cuttlefish and devices (Phase 3 onward): the same memory search on
  guest RAM after lock with real apps opted in; criterion 2.6.
