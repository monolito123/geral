# ADR-0006: Build reproducibility

- **Status:** Accepted (2026-11-12; decided under the owner's delegation)
- **Date:** 2026-11-12
- **Decider:** project owner (delegated)

## Context

The brief requires reproducible builds, pinned toolchains and a build that
anyone can repeat to confirm published hashes. Reproducibility is also what
makes the integrity folder meaningful: a hash proves something only if an
independent party can arrive at it.

Today only host tools exist. This ADR fixes the rules they follow and the
rules OS images will follow.

## Options considered

### Option A — best effort

Avoid obvious sources of variation and compare builds occasionally.

- Cheap. Drifts unnoticed.

### Option B — reproducibility as a gate

Every change must pass a check that builds twice under deliberately
different conditions and compares the output bit for bit.

- A regression is caught by the change that causes it.
- The check costs a second build.

## Decision

**Option B.**

Rules for all builds:

1. **Pinned inputs.** The Rust toolchain version is fixed in
   `rust-toolchain.toml`. Dependencies are fixed in `Cargo.lock` with
   checksums. CI actions are pinned by commit hash. The AOSP manifest will
   pin exact revisions (ADR-0004).
2. **No network during the build.** Fetching is a separate first step that
   downloads only what the lock file names and verifies each checksum. The
   build then runs offline.
3. **No ambient paths, times or names in outputs.** Source and Cargo
   directories are remapped to fixed prefixes. Embedded timestamps come
   from `SOURCE_DATE_EPOCH`, set to the time of the last commit. Archives
   are written in sorted order with fixed ownership.
4. **The check must be able to fail.** `nott repro` builds the same source
   in two directories of different depth, with two different Cargo homes,
   and requires identical output. Without the path remapping that same
   procedure produces different binaries, which is how the check was
   validated.
5. **Outputs name their inputs.** The SBOM is generated by the build and is
   itself deterministic.

Scope today, stated plainly:

- **Verified:** the host tools are bit-for-bit identical across different
  source and Cargo paths on one machine.
- **Not yet covered:** different machines. The linker and C library come
  from the host, so two hosts with different versions may produce different
  binaries. Closing this needs a pinned build environment (a container or
  image identified by hash), which is defined together with the AOSP build
  host.
- **Not yet covered:** dependencies are fetched, not vendored. The lock
  file's checksums protect their integrity, but a build needs the registry
  to be reachable once. Vendoring them into the tree is planned for when
  the project has its own repositories.
- **OS images:** AOSP has its own reproducibility support `[K]`. How well a
  NottOS image reproduces is unknown until one is built.

## Consequences

- **Positive:** every change is tested for reproducibility; the digest of
  the host tool is printed by the check, so two machines can be compared by
  eye.
- **Negative:** the check doubles build time for the host tools (about half
  a minute today).

## Revisit when

The pinned build environment exists (extend the check to two machines) and
when the first OS image is built.

## Verification

`./nott repro`, run locally and in CI. Results are in the Phase 1 report.
